1. Purpose

This guide defines the recommended verification procedure for ORL-Money v2.1.0.

The verification model separates:

`producer execution`

`producer self-verification`

`browser conformance and regression audit`

`Python/browser declared-reference parity`

`independent reconstruction`

`canonical-byte verification`

`frozen corpus verification`

`artifact byte identity`

A successful behavioral check does not by itself prove artifact identity.

A matching SHA-256 hash does not by itself prove behavioral correctness.

The activities serve different purposes.

11. Independent Verification Meaning

The independent verifier does not import:

`demo/ORL_Money_Reference_Kernel_v2_1_0.py`

It independently reconstructs the declared bundle structure from the bundle's embedded inputs.

A PASS confirms agreement between:

`supplied bundle`

and:

`independently reconstructed bundle`

under the independent verifier's implementation of the declared v2.1.0 contract.

This is stronger than trusting producer self-verification alone.

It does not prove:

- input truth
- account ownership
- authorization
- legal validity
- settlement
- universal financial correctness
- production security

16. Verifier Intake Boundary

The verifier reads JSON as UTF-8 and rejects duplicate object keys.

The current maximum input file size is:

`16 MiB`

The verifier may report bounded failures for:

- missing file
- file read failure
- input size above the declared limit
- invalid UTF-8
- duplicate JSON keys
- invalid JSON
- non-standard JSON constants
- unsupported nesting
- non-canonical JSON bytes when strict mode is enabled

This boundary improves public-input behavior but does not claim complete hostile-input or denial-of-service resistance.

30. Verifier Exit Codes

The command-line verifier uses:

`0 = verification or self-test PASS`

`1 = verification, corpus, data, intake, or file-access FAIL`

`2 = command-line usage error or missing mode`

Missing files, unreadable files, invalid UTF-8, malformed JSON, duplicate JSON keys, canonicalization failures, and verification mismatches therefore return exit code `1`.

Exit code `2` is reserved for command-line usage errors, such as invoking the verifier without selecting a supported verification mode.

These exit codes support scripting and continuous verification workflows.

33. Meaning of SHA-256 Verification

A matching SHA-256 confirms:

`local file bytes = frozen file bytes`

under the compared digest value.

It does not by itself establish:

- correct behavioral output
- independent reconstruction
- valid source data
- authorization
- settlement
- security
- production readiness

Behavioral verification and artifact identity verification remain separate.

35. Failure Conditions

Treat verification as failed if any applicable condition occurs:

- a reference implementation does not execute
- a declared audit group fails
- a reference scenario differs from its expected state
- Python/browser declared-reference parity fails
- the independent verifier reports FAIL for an expected valid bundle
- supplied and reconstructed financial resolution identities differ
- supplied and reconstructed financial bundle identities differ
- a tampered bundle is incorrectly accepted
- a declared corpus bundle hash differs from the manifest
- strict canonical verification fails for the canonical frozen corpus
- a frozen artifact hash differs from `hashes/SHA256SUMS.txt`

A failed check indicates that further investigation is required.

It does not by itself identify the cause.
